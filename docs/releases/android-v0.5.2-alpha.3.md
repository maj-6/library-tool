# Library Tool Capture 0.5.2-alpha.3

Prerelease. `versionCode` 34.

Supersedes the unpublished `0.5.2-alpha.2`, and includes everything from
`0.5.2-alpha.1` (Android cloud capture sync), which is now merged to `main`.

## CH matching runs on the phone

After extraction, `ProcessWorker` looks the book up in the CH master list and
records the verdict beside the entry. It is entirely offline: the list ships in
the APK as `assets/ch_index.json` (5264 rows, ~640 KB once the APK's own zip
deflates it) with the posting lists the candidate generator needs, so a match
appears on a shelf with no signal.

The asset is deliberately not pre-gzipped. The Android build un-gzips a `.gz`
asset and packages it under the stripped name, so a `ch_index.json.gz` in the
source tree becomes `assets/ch_index.json` in the APK and the app's open() of
the `.gz` name fails on device — while every host-side test still passes,
because they read the source tree. `ChIndexTest` now guards the asset name.

The index is generated by `tools/build_ch_index.py` from the same functions the
desktop matcher uses, and it carries the thresholds with it rather than letting
the phone hardcode values the desktop owns.

### Why the port is trustworthy

The acceptance thresholds in `catalog_checks.py` were tuned against
`difflib.SequenceMatcher.ratio()`, so a Kotlin approximation of that function
would silently move every decision boundary while still looking plausible.
`ChMatcherConformanceTest` therefore checks the port against ratios produced by
the real Python — 794 similarity pairs, 400 author cases and 900 acceptance
decisions — to 1e-12, including degenerate inputs and the hard negatives where
two different books share a prefix.

One detail worth recording: `difflib`'s autojunk heuristic engages at 200+
elements, and CH's longest title is 212 characters, so it genuinely fires on
real rows. The port implements it rather than assuming titles are always short.

`ChIndexTest` additionally parses the asset that actually ships and searches it,
so a truncated or stale regeneration fails the build instead of a device.

## Merging an approved match

Approving contributes the publisher, city, edition, page count, condition,
illustrations, price and subject keys CH holds. Two rules govern it:

- **A blank never overwrites.**
- **A disagreement is never resolved silently** — your value came off the title
  page, CH's came from a catalogue with known-dirty rows, so a conflict keeps
  yours and shows CH's beside it, marked as not applied.

CH's acquisition `DATE` is deliberately not offered: it describes CH's purchase,
not the book.

A rescan preserves a decision when the same row matches again, and resets to
undecided when a different row does — carrying a decision across two different
books would approve something the user never saw.

## Known gaps

- The WHL and Internet Archive indicators still render from desktop-supplied
  metadata already synced to the entry. Moving those checks to the cloud so they
  run as books are scanned is not in this build.
- The index is a build-time snapshot. Changes to the CH list reach the phone
  only through a new APK; there is no incremental update path yet.
